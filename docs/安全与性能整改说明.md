# 安全与性能整改说明

## 1. 检查结论

本次针对项目的配置与向量检索核心链路进行了静态审查，识别出以下主要问题：

1. **潜在安全风险：默认 API Key 硬编码**
   - `qdrant_api_key` 在默认配置中为固定明文值，存在误提交、误暴露风险。
2. **检索排序异常：分数被整数截断**
   - 原实现中 `hit.score` 被 `int()` 截断，许多低于 `1` 的有效分数会归零，导致时间衰减后排序失真。
3. **可观测性不足：使用 `print` 而非结构化日志**
   - 异常与初始化流程输出缺乏统一日志级别，不利于线上排障。
4. **哈希碰撞风险：使用 MD5 生成文档 ID**
   - MD5 抗碰撞能力弱于 SHA-256，理论上存在冲突风险。

## 2. 已实施整改

### 2.1 安全整改

- 移除默认硬编码的 Qdrant API Key，改为 `None`，由环境变量注入。
- 调试日志仅输出非敏感信息（例如 Host 和 Port），避免泄露凭据。
- 将文档 ID 哈希算法从 **MD5** 升级为 **SHA-256**。

### 2.2 异常处理与可运维性

- 将启动连接失败、集合初始化等关键路径统一为 `logging` 输出。
- 保持“启动容错”策略：Qdrant 不可达时记录警告但不中断 API 进程。

### 2.3 性能与检索质量优化

- 修复 `int(hit.score)` 截断问题，改为 `float(hit.score)` 参与时间衰减。
- 检索最终得分采用 `reranker_score * decay_score`，使时间因素与语义重排协同生效，提升结果稳定性。

## 3. 建议后续动作

1. 在生产环境启用 HTTPS/TLS（建议通过网关或服务网格统一处理）。
2. 引入自动化安全扫描（如 `bandit`、`pip-audit`）纳入 CI。
3. 为检索排序补充单元测试，覆盖：
   - 小数分数样本；
   - 时间衰减边界值；
   - reranker 空结果场景。

## 4. 影响评估

- **兼容性**：API 入参与响应结构未变，更改集中于内部实现。
- **安全性**：凭据泄露面与哈希碰撞风险下降。
- **检索效果**：排序逻辑更符合预期，减少“高相关内容被错误降权”的情况。
